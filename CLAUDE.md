# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`~/.om` is the install root (`$OM_HOME`) of **om**, a zero-daemon workspace orchestrator on Podman or Docker + Caddy, for Linux/macOS/Windows. One static Go binary (`cmd/om`, Go standard library only: no dependencies, no cgo). The repo is Go (plus shell and PowerShell for the installers) and nothing else: the original Python implementation is no longer in the tree, only in the history (its last commit on `main`, `9b19235`), which `testdata/e2e/record.sh` checks out into a throwaway git worktree to re-record the end-to-end goldens; `internal/repocheck` fails if a `.py` file or a Python call comes back. Machine state lives outside it (`internal/state`): settings in `$OM_CONFIG_DIR/om.env` (default `~/.config/om/om.env`, a folder other tools may share — om only ever touches `om.env`), everything generated in `$OM_STATE_DIR` (default `~/.local/state/om/`: `runtime.env`, `ports.yml`, `data/` with the Caddy root CA key and edge token, `routes/`, `auth/`, `registry/`, `firewall/`, `logs/`, `bin/om-dashboard`). Pre-split installs are migrated once by `ensureStateMigrated` (`internal/cli/main.go`, `internal/migration`). Never write state into `~/.om`. om refuses to run as root (`App.Main`): containers stay rootless under the user; only `om firewall`, `om boot` and the installer's port step call sudo.

## Commands

- Build: `CGO_ENABLED=0 go build -o build/om ./cmd/om` (`install.sh` does it, or downloads the release binary and checks its SHA-256). Lint: `gofmt -l .` must print nothing and `go vet ./...` (also with `GOOS=darwin` and `GOOS=windows`) must be clean; CI runs both as the `lint` job.
- Tests (no container engine needed): `go test ./...`; one package: `go test ./internal/routes`; with the race detector (CI): `go test -race ./...`. Most library tests replay **goldens recorded from the original Python implementation** (`testdata/golden/`, `testdata/e2e/`; the end-to-end ones re-recorded by `testdata/e2e/record.sh`, the library ones recorded once from that program's last commit): a Go port is right when it prints exactly what Python printed. `internal/cli/e2e_test.go` runs a stateful scenario through the built binary against a fake `podman`. Real-engine behaviour is checked by CI's `integration` job and `om doctor`.
- Cross-platform rules (behavior must be identical on every OS): text files are UTF-8 with `\n` (line endings pinned by `.gitattributes`); `state.Run` decodes subprocess output as UTF-8 and never fails for a missing binary (code 127); host paths handed to compose go through `settings.ComposePath` (forward slashes); the engine socket comes from `Engine.EngineInfo` (VM-side path for podman machine). `internal/py` holds the few Python behaviours om's files depend on (`str.strip`, `json.dumps(indent=2, sort_keys=True)`, ordered objects): use it instead of reimplementing them.
- Coverage floors (CI `coverage` job): the library (everything but `internal/cli` and `cmd/om`) and the whole program, set in `.github/workflows/ci.yml`. Raise them when coverage rises; never lower them to pass.
- `om doctor` checks install + security perimeter (live attack probes) and prints fixes — run it after any network/core change. The probes that run inside containers are `om probe …` (`internal/probe`), the om binary mounted at `/om` in the pinned Alpine image.
- Core: `om core start|stop|restart|reload|update|heal|status` (`heal` is run by the `om boot enable` timer; `Core.Down` writes `<state>/data/stopped` so heal never revives a deliberately stopped core) — always via om (it writes `<state>/runtime.env`, `ports.yml` and `dashboard-mounts.yml` and passes them to compose); plain `podman compose up` in `core/` fails on the `${VAR:?}` guards by design.
- The dashboard is `om dashboard` (`internal/dashboard`, the page embedded with `go:embed`) running in `om_dashboard`: `om core start` copies the Linux build of om to `<state>/bin/om-dashboard` (on macOS/Windows it needs `build/om-linux-<arch>` next to `om`, which the installers make) and the container mounts that folder at `/om`. After a change: rebuild, then `om core restart dashboard`. Never a plain `podman restart` from a shell on Linux: the container takes the caller's `oom_score_adj` (shell 0, systemd user units 200), and podman's healthcheck timer (200) then cannot exec into it (runc: "failed to update /proc/self/oom_score_adj"), so it turns unhealthy. om starts/restarts containers through `Engine` lifecycle functions, which for local Podman first raise om's own `oom_score_adj` to the units' value (other engines: unchanged). Never run `podman start|restart` inside a systemd unit (`systemd-run`): podman keeps conmon in that unit and systemd SIGKILLs it when the unit ends, leaving the container unmonitored.
- Workspace commands (`start`, `add`, `sync`, …) need a directory containing `.om/config.json`.
- Front-door host ports come from `Settings.EdgePorts` (`OM_HTTP_PORT`/`OM_HTTPS_PORT`, default 80/443); print URLs with `Settings.BaseURL`, never a literal `http://localhost/`. Container-side ports (80/443/8080/8443) are fixed.
- Images are pinned to exact versions plus the multi-arch index digest (core: `tag@sha256:…`, from the registry, never a local platform digest) or major/minor (scaffolds); never introduce `latest` or bare-major tags. A test holds `core/compose.yml` and the Containerfiles to digest pins.
- `om docs` reads `docs/*.md`, `README.md`, `CHANGELOG.md`. Docs: `docs/START.md` (the ten-minute path for newcomers), `docs/GUIDE.md` (every user workflow), `docs/TROUBLESHOOTING.md` (symptom, cause, fix), `docs/GLOSSARY.md`, `docs/ARCHITECTURE.md` (network and security mechanics), `docs/DESIGN.md` (why, laws, limits), `docs/adr/` (decisions), `docs/REMAINING.md` (open items before a public release: update it when one is done). Put new content in the one that fits; don't add parallel docs. `docs/COMMANDS.md`, `SETTINGS.md`, `LABELS.md` and `DOCTOR.md` are generated by `go test ./internal/cli -run TestReferenceDocs -update` from the command table (`internal/cli/commands.go`), `settingAbout`, `scaffold.ActiveLabels` / `LabelMenu` and `doctorDocs` (`internal/cli/refdata.go`): never edit them by hand; the test fails while they are stale. `internal/attacks` holds the attack and fuzz tests (hostile names, labels, snippets and compose files) and `internal/repocheck` also holds the docs to the code (links and anchors resolve, every setting, label, dashboard route and package is documented, the changelog has an entry for `state.Version`) and keeps the CI workflows pinned and the packages layered.

## Architecture

Keyed on a **workspace id** (`.om/config.json` → `workspace_id`, default dir name; must match `workspace.IsSafeName`, `core` reserved).

1. **CLI** — `cmd/om` calls `cli.App.Main` (`internal/cli`): the argparse-compatible parser (`argparse.go`, `format.go`, `commands.go`: the same accepted forms, errors and help layout as the Python original), `Dispatch`, and the `cmd*` functions grouped by job (`ws.go` start/stop/update/lock, `core_cmds.go`, `inspect_cmds.go`, `sync_cmds.go`, `cfg_cmds.go`, `host_cmds.go`, `sec_cmds.go`, `egress_cmds.go`, `author_cmds.go`, `preview_cmds.go`, `doctor.go`, `refdocs.go`). `App` holds the services; every outside effect (running a command, the clock, sleeping, the terminal) is an injectable function so tests drive the whole program. Library packages in `internal/`, each named for what it holds: `py` (Python-compatible text and JSON), `state` (paths, constants, `FileLock`, `Run`, atomic/private writes, `Version`: the base every package imports), `registry` (workspace registry, stable web and stream port slots, address policies), `workspace` (ids, config, compose-folder discovery, compose env), `engine` (engine detection, networks, `ConnectRouter`, lifecycle, reviving dead containers, `om core watch` support), `netdetect` (LAN address, tunnels by kernel kind, PTR names), `settings` (`om.env` resolution `auto/off/value`, the VPN as configured, `RenderPorts`, runtime env), `migration` (pre-split state), `core` (the core's lifecycle: up, down, heal, watch, runtime files), `labels` (a compose service's labels as a map, whichever form the file uses, plus `om.mem|pids|cpus` limits; every package reads labels through it), `stream` (raw TCP stream tier labels, HAProxy edge/router fragment generation and validation, stream port allocation), `network` (workspace networks, validated edge reload that recreates the edge if its single-file Caddyfile mount is stale), `gitsync` (drift, `SyncWorkspace` with reconcile callback + health check + rollback), `secrets` (reads legacy `om-v1`/`om-v2` vault files only; age secrets via the local `om-tools` image from `core/tools/`, decrypted to `$XDG_RUNTIME_DIR` and mounted via a compose `secrets:` override; logins and signers), `routes` (compose labels → route options, `om.caddy` validator, `RenderVhost`/`RenderAlias`), `routesync` (compose files → Caddy route files, pruning orphans), `scripts` (`om scripts` discovery), `policy` (deploy gate on `compose config`), `egress` (om_egress config/credentials), `lock` (`.om/lock.json`, registry digests and build date/size via the OCI API, `om.update` modes), `generations` (signature check against the trusted signer copy, hash-chained generation log), `firewall` (nft/pf/Windows rules and their application), `sched` (autosync systemd/launchd/schtasks, boot), `links` (cross-workspace links), `notify` (desktop/webhook messages, de-duplicated by key, always `notify.log`), `scan` (trivy/grype counts), `prune` (unused images), `previews` (`om preview` worktrees), `scaffold` (`om add`: validation and the compose text, pure functions). `core/egress/Containerfile` builds the `om_egress` image (`Egress.Image` / `EnsureImage`, built by core start).
2. **Global core** (`core/compose.yml`) — `om_caddy` (HTTP edge; publishes 80/443 and service ports, **only** on `om_core_net`), `om_router` (on `om_core_net` + every `<ws>_net`), `om_stream_edge` (raw TCP edge; publishes stream ports, **only** on `om_core_net`), `om_stream_router` (raw TCP router on every `<ws>_net`, no network listener, connected to edge via Unix sockets in `om_stream_sock`), `om_egress` (Squid on `om_core_net` + every internal `<ws>_net`; config rendered by `internal/egress` into `<state>/egress/`), `om_sockguard` (no network; read-only filtered engine socket for the dashboard), `om_dashboard`. The network boundary is the developer's VPN: `netdetect` finds every tunnel by kernel kind (never by product name), `OM_VPN` lists the ones trusted with `om vpn trust` (none by default), names come from a PTR query. Never hardcode a VPN product; om builds no VPN, login system or device CA (docs/adr/0003).
3. **Dashboard** — `internal/dashboard` (`net/http`; container listing via `om_sockguard`'s filtered socket, never the raw engine socket) + the embedded `index.html`. `internal/dashboard/testdata/golden.json` is a recording of the Python server's answers to 70 requests; `TestMatchesPython` replays it.

### Routing is generated, not hand-written

`routesync.Syncer` writes into `$OM_STATE_DIR/routes/` (mounted at `/etc/caddy/conf.d`) from each workspace's compose files (`routes.ConfigMeta` on the engine's `compose config`, `routes.ParseServiceMeta` regex fallback without an engine; both in `internal/routes`: `dashboard.port` label > exposed port > 8080; public only with `dashboard.scope=public`):
- `<ws>-<svc>.caddy` — `http://<ws>.<svc>.localhost` plus the service's own ports: `http://:20000+slot` (private: loopback and VPN) and, if public, `http://:21000+slot` (LAN and VPN), each aborting a Host outside `{$PRIVATE_NAMES}` / `{$PUBLIC_NAMES}`. Slots are stable, in `<state>/registry/service_ports.json` (`Registry.AssignSlots`; the dashboard reads it). Stream tier slots (22000+n) and explicit stream ports are registered in `<state>/registry/stream_ports.json` (`Registry.AssignStreamSlots`; HAProxy fragments in `<state>/stream/`). `<ws>-<svc>.private_alias` / `.public_alias` — redirects from `/<svc>` and `om.route.aliases` on the dashboard's address to the service's port. One origin per service (docs/adr/0004); never route a service as a path on a shared origin.
- Change `routes.RenderVhost`/`RenderAlias`, never the generated files. om's own hand-written routes (`00-info.caddy`) are program files in `core/caddy/conf.d/`, mounted at `/etc/caddy/core.d`.
- Routes of a workspace whose folder is gone are pruned by `Syncer.PruneOrphanRoutes` (on `om start`, `om core start|restart|reload`) unless its containers may still run; `om doctor` reports them. The header `# Service: <svc> (<ws>)` records ownership; only owned files are written/pruned — keep that format.

### Security model (do not regress)

- Tiers: loopback → edge `:80/:443`, VPN addresses (`OM_VPN`, trusted with `om vpn trust`) on host 80/443 → edge `:81/:444` (`state.VPNHTTPPort`/`VPNHTTPSPort`; private: explicit host list + final `:80`/`:81 { abort }`, optional `basic_auth` via `import private_auth`; `<ws>.<svc>.localhost` sites exist on edge :80 only, i.e. this machine); LAN, and VPN addresses on host 8080/8443 → edge `:8080/:8443` (public: only `*.public_subpath`, sets `X-Access-Scope: public`). The dashboard strips private data for public scope, enforces a Host allowlist and CSRF checks.
- Edge → workspace services **only** via `import to_workspace <ws>_<svc>:<port>` (a unix socket in volume `om_router_sock`: the router has no network listener at all), which sets `X-Om-Edge-Token` (secret in `<state>/data/edge_token`) and `X-Om-Upstream`; `core/caddy/router/Caddyfile` aborts anything without the exact 64-hex token or with an `om_*` / malformed upstream. Never attach `om_caddy` to workspace networks and never `reverse_proxy <ws>_<svc>` directly from the edge.
- Services use `expose:`, never `ports:`. Core containers are `read_only`, `cap_drop: ALL` (+`NET_BIND_SERVICE`, required by the caddy binary's file capability under no-new-privileges).
- Firewall (`om firewall`) uses its own nft table `inet om_guard`; never `flush ruleset`.

### Compose conventions

`workspace.DiscoverComposeDirs` finds compose files at the workspace root and depth 1–2, ordered by a `# priority: N` line; a folder containing `.omignore` (and everything below it) is skipped. Labels drive the dashboard: `dashboard.name|icon|description|port|scope|hide|web|path|search|search_url`, `workspace.id`, `om.core`.
Labels also shape routes (`routes.RouteOptions`): `om.route.keep_prefix=true` (the app serves under `/<svc>/`; its root redirects there), `om.route.aliases=/a,/b` (redirect top-level paths on the dashboard's address to the service's port, `{uri}` kept), `om.route.dashboard_paths=/api/x*` (paths on the vhost served by the dashboard). Label paths are validated (`internal/routes`) before they reach Caddy. `om.tcp=<container-port>` and optional `om.tcp.port=<host-port>` declare raw TCP stream routes, mapped via Unix domain sockets between `om_stream_edge` and `om_stream_router` without network exposure on the router. `om.egress=host,*.host|learn|internet` gives a service its own `om_egress` credential via an om-generated compose override (`<state>/egress/overrides/`). `om.link=<ws>/<svc>` + `om.link.allow=<ws>/<svc>|<ws>/*` (both sides) make a two-container link network (`internal/links`). A service folder's `om.caddy` holds its own Caddy rules, checked by `routes.ValidateSnippet` (allow-list; fail closed). `om preview <branch>` = a git worktree in `<state>/previews/` with its id in `.om/local.json` (the workspace id is read from it first). `--json` output goes through `App.EmitJSON`. Every compose folder runs on its own internal network `<ws>_<folder>_net` (`network.Net.ProjectNetwork`: a compose override maps the network naming `<ws>_net` and the implicit `default` to it, makes the file's own networks internal with a per-folder name (compose would name them after the workspace and share them), and joins every other service to it; another stack's external network is the policy rule `networks`; router/egress attached via `Engine.ConnectRouter`, which includes `Engine.ProjectNetworks`; folders that are gone are pruned on a full `om start`); `om.network=shared` keeps a folder on `<ws>_net`, `om.link` joins two services. Any command that (re)creates containers must go through `App.startWorkspace` (overrides: egress, lock, secrets, network) — never a bare `compose up`. Logging never stores content: edge `(access_log)` deletes URL/headers/client fields, `om.log=off` → `log_skip` on every site, no `om-in` firewall log for its ports (`Registry.NoLogPorts`) and `logging: driver: none` for the service (`nologOverride`); both Caddyfiles filter their *default* logger too (error entries would carry the URL and the edge token); refusals are always logged (`om-refused`), each by its own log rule before the drop (never `limit` on a drop). `om_egress` joins only networks recorded in `<state>/networks/egress.json` by `om start`. VPN devices are discovered by `Settings.VPNPeers` from the kernel's routes/neighbours through the trusted VPN interfaces (never a product CLI) and named by PTR. `OM_VPN_ALLOW` (`om vpn allow|disallow`) limits the VPN's private tier to listed devices: an address rule like `om.net`, and while unenforced `ports.yml` leaves the VPN's private tier unbound; the other devices' new connections to host 80/443 on a VPN address are sent to 8080/8443 (`internal/firewall` VPN fallback: nft `chain vpn_public` dnat, pf `rdr`; not on Windows). `om.net.allow=<ip|cidr>,…` / `om.net.deny=…` restrict who reaches a service's own ports (`om.net.allow=vpn` = the OM_VPN_ALLOW devices, stored as the word and expanded by `internal/firewall` at render time), enforced by the host firewall only (the edge sees every client as one internal address under rootless port forwarding; `om.caddy` refuses `remote_ip`/`client_ip`): `<state>/registry/net_policy.json` → the `internal/firewall` renderers; fail closed (unreadable label → no route; rules not in the applied firewall → no own ports). `om_guard` renders every address rule twice: input chain, and a forward chain matched on `ct original` for engines that publish by DNAT (rootful); both must be applied. `om add` scaffolds are least-privileged (non-root nginx-unprivileged on 8080 / Node with `cap_drop: ALL`, `read_only`, tmpfs `/tmp`; `--image` keeps CHOWN, DAC_OVERRIDE, FOWNER, SETGID, SETUID). `om.update=hold|auto` (hold keeps an image's pin; auto: the scheduled sync moves it, health-checks, reverts the lock commit on failure) and `om.mem|pids|cpus` (a compose override from `internal/labels`, passed by `startWorkspace` with the others). Every core container has a memory and pids limit and a healthcheck; `om_egress` and `om_dashboard` carry `om.heal=restart`; `om core heal` writes `<state>/registry/core_memory.json` (anonymous memory) for the dashboard's RAM tile. `om.policy.allow=<rule>,…` waives policy-gate rules (`internal/policy`: `Waivable`; `privileged`/`ports` are laws) for that service only.

**om is generic, like git.** Never special-case a service or workspace name, a hostname or a user path in om's code: if a service needs different behavior, add or use a label and set it in the workspace's compose file. om touches the host only in the explicit opt-in commands (`om firewall`, `om boot`, `om autosync`); it never edits files like `/etc/hosts`. Workspace-specific docs live in the workspace, not in `docs/`. `App.wsEnv` injects `WORKSPACE_ID`, `COMPOSE_PROJECT_NAME`, `WORKSPACE_ROOT`, `DATA_DIR`, `WORKSPACE_DATA`, `WORKSPACE_NET`, `DOCKER_SOCK`. Machine-local workspace state (`.om/local.json` autosync switch, `.om/state.json`, `.om/trash/`) is hidden via `.git/info/exclude` so it never dirties the repo (a dirty tree blocks `om sync`).

## Token-saving rules

### Reading files
- Search for the function or keyword first (grep), then read only
  those lines, not the whole file
- Don't re-read a file already read in this session unless it changed
- Skip node_modules, dist, build, .git, lock files, and minified
  files unless I ask or you're debugging an error that points there
- Skip log files unless I ask or an error message references them

### Working
- Make the smallest change that fixes the problem; don't refactor
  or reformat code I didn't mention
- Don't create new files unless needed
- Run only the test file related to the change; run the full
  suite once at the end
- If a task touches more than 3 files, stop and show a plan first

### Answering
- Keep replies under 5 sentences unless I ask for detail
- Don't repeat my question back or summarize what you just did
- Show only the changed lines, not the whole file
